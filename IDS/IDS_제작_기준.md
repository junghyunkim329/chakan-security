# CAN IDS 제작 기준

문서 기준일: 2026-11-24

대상: Phase 7 공격·IDS 담당자

상태: CAN A1~A8의 목표 기준과 데이터셋·대시보드·IDPS 확장 방향을 정리한다. 외부 AutoHack용 C11 코어와 Python 분석·평가 도구 v1을 구현하고 네 규칙의 파일 평가를 완료했다. 전체 SIL 시나리오·native SocketCAN 수집·가상 CAN 재생·대시보드·IDPS는 후속 범위다.

## 1. 목적과 적용 범위

정상 주행 CAN 트래픽에 A1~A8 공격 시나리오를 적용하고, IDS가 어떤 조건을 탐지하고 어떤 근거를 남겨야 하는지 정한다. 구현자는 이 문서로 입력 정의, 탐지 규칙, 기대 이벤트와 시험 항목을 연결한다.

2026-11-24 사용자 지시에 따라 CAN 데이터셋 기반 실험을 포함한다. 기존 SIL 규칙과 외부 데이터셋의 적용 기준을 구분하며, 데이터셋별 정의와 지원 여부는 §3.3에 따른다. 데이터셋 활용을 실제 ECU·Gateway 관측 실험 완료로 표현하지 않는다.

2026-11-24 사용자 확정: **실제 데이터와 확인한 차량 동작을 기준으로 IDS를 제작하며, 기존 프로젝트 가정·선택값과 충돌하면 실제 데이터를 우선한다.** [project.md](../project.md) §2.1.1에 이 우선순위를 반영한다. 실제 데이터에 맞춰 기준서·해당 configuration·이 문서를 함께 수정하고, 확인되지 않은 OEM 값을 임시로 만들지 않는다. 사용자 제공 「08. 공격 시나리오 계획」의 **CAN A1~A8**을 이번 범위로 한다. DoIP/UDS B1~B3, SOME/IP C1~C3, LIN D1~D2의 탐지 규칙은 후속 범위다. 단, 같은 CAN에서 정상적으로 흐르는 ISO-TP 진단 트래픽은 구분해야 한다.

IDS는 이상을 탐지하고 기록하며, **대시보드 연동과 향후 IDPS 확장**을 고려해 제작한다(2026-11-24 사용자 지정, `project.md` §10.1). 탐지·기록·표시를 구분하고, 이후 예방 정책과 실행 결과를 연결할 수 있게 한다. 현재 단계에서 자동 대응을 활성화하지 않으며 구체적인 차단 방식과 권한은 후속 설계에서 확정한다.

§4·§5.1의 ID·주기·범위·임계값·1초 합격 시간은 현재 SIL의 **프로젝트 선택값**이다. RAV4의 OEM 요구사항이나 R155가 지정한 수치가 아니다. SIL 시험에는 현재 공통 CAN 정의를 사용하며, 주 데이터셋 AutoHack에는 해당 차량·버스의 실제 원본과 확인한 정의를 사용한다. `project.md` §2.2의 RAV4 가솔린 전환은 아직 완료되지 않았으며 전환 시 counter/checksum·주기·범위와 fixture를 다시 검토하고 검증한다.

## 3. 입력과 관측 기준

### 3.1 입력 분류

| 구분 | 현재 ID | 적용할 검사 |
| --- | --- | --- |
| 주기 PDU | `0x100`, `0x110`, `0x180`, `0x200` | DLC, 프로젝트 CRC, reserved, counter, validity, 범위, 주기·횟수 |
| ISO-TP 진단 | Engine `0x7E0/0x7E8`, Brake `0x7E1/0x7E9` | 정상 등록 ID로 구분. 주기 PDU의 byte 6 counter·byte 7 CRC·주기 규칙을 적용하지 않음 |
| 설계에만 있는 PDU | `0x280`, `0x600` | 정의 미완료. 지원 완료·정상 송신 중으로 가정하지 않으며 적용 전 사용자 결정 필요 |
| 그 밖의 ID | 예: `0x123`, `0x7FF` | 실행 구성의 등록 목록에 없는지 확인한 뒤 A2 판정 |

등록되지 않은 ID를 검사할 때 `can.yaml`의 네 PDU만 전체 allowlist로 사용하면 정상 진단을 오탐한다. 반대로 진단 ID라는 이유로 모든 내용이 정상 또는 인증됐다고 간주하지 않는다. 진단 내용의 보안 검사는 후속 범위다.

### 3.2 관측 위치와 시간

- Gateway가 거부한 frame도 IDS 근거에 남아야 한다. 검증 후 정상 SOME/IP 값만 보고 CAN 공격을 평가하면 안 된다.
- 기존 capture 기준은 `ns_vehicle`의 차량측 CAN 관측이다(`project.md` §4.2). IDS 수집 프로세스의 실제 배치와 AP로의 전달 경로는 §10에서 별도로 확정한다. AP에 CAN 직접 접근권을 추가하지 않는다.
- 관측 정보에는 namespace/interface, CAN ID, frame 형식, DLC, 원본 payload, monotonic 관측 시각을 보존한다. CAN FD·29-bit ID·RTR·error frame을 정상 Classical 11-bit PDU로 해석하지 않는다.
- 기간·window·탐지 지연은 monotonic clock으로 계산한다. 사용자용 시각에는 timezone을 넣는다.
- 공격 label은 시험 실행기가 별도로 기록한다. IDS가 label의 공격 종류·시작 시각을 읽고 이벤트를 만들면 탐지 시험으로 인정할 수 없다.
- 수집 누락, IDS 재시작, queue 적체 또는 기록 실패가 있으면 그 구간의 오탐·미탐 결과를 정상 측정 결과로 취급하지 않는다.

### 3.3 외부 CAN 데이터셋 적용 기준

관련 자료는 Notion [08 공격 도구와 IDS 회의록](https://app.notion.com/p/40c3c28c0c7a80478e33d0f09c0e3385)과 [CAN Dataset](https://app.notion.com/p/40f3c28c0c7a804eae9cc29e99f20934)이다. **2026-11-24 사용자 재확정: AutoHack은 IDS 제작·평가의 주 데이터셋과 주 참고 자료, HCRL Car-Hacking은 비교용·우선 파일 분석 대상, ROAD는 규칙 기반 탐지의 한계 분석 근거다.** AutoHack 원본 확보가 지연되어 HCRL부터 분석했으며 주 데이터셋 변경을 뜻하지 않는다. 실제 배포 판·차량·버스·파일 목록은 확보한 원본으로 고정한다. 전체 시나리오와 AutoHack의 적용 범위는 [공격 시나리오별 탐지 범위](docs/evidence/attack-scenario-coverage.md)에 정리한다.

2026-11-24 사용자 확정 순서는 **① 파일 직접 분석으로 IDS 검증 → ② 해당 데이터의 가상 CAN 재생으로 수집·탐지·대시보드 연동 검증**이다. 1단계에서 원본 형식·시간·라벨과 규칙 적용 가능성을 확인한 뒤 2단계의 변환·버스 매핑·재생 속도를 정한다. 두 단계에서 같은 입력과 정책을 추적하되 재생 지연·누락과 속도 변환의 영향을 별도로 보고한다.

| 구분 | 고정할 내용과 적용 경계 |
| --- | --- |
| 출처·재현성 | 제공기관의 원본 설명, 사용 조건·인용, 배포 판, 파일 목록·hash, 차량/버스와 정상·공격 범위를 확인해 manifest에 연결한다. Notion의 추천 설명만으로 실제 파일 구성을 단정하지 않는다. |
| 입력 해석 | 실제 timestamp 단위·정밀도·기준, ID 표기·frame 형식, DLC·payload, 버스 구분, 라벨 의미를 원본 명세와 파일로 확인한다. 형식이 다른 파일은 명시적인 입력 변환으로 처리하고 원본 위치를 보존한다. |
| 프로파일 구분 | 외부 차량에는 §3.1·§4·§5.1의 프로젝트 ID 목록, DLC 8 공통 가정, byte 6 counter·byte 7 CRC, 신호 범위와 10/20ms 주기를 그대로 적용하지 않는다. 차량·버스별 정의·정상 기준을 확인해 별도 적용 여부를 확정한다. |
| 규칙 적용 가능성 | A1~A8을 각각 원본 공격·라벨·입력 정보에 매핑한다. DBC·공개 checksum/counter 정의 등 근거가 없는 A3 reserved·A4 물리 범위·A5 CRC·A6 counter 검사는 지원 불가/확인 대기로 표시한다. 원시 payload 변화만으로 해당 공격을 확정하지 않는다. |
| 정답 분리 | 원본 라벨이 주입 frame인지 공격 구간인지 먼저 확인한다. 탐지기로 전달하는 입력에서는 라벨·공격 파일명 등 정답을 노출하는 정보를 제외하고 사후 평가기에만 전달한다. 라벨 없는 구간을 임의로 정상 정답으로 만들지 않는다. |
| 시간 | 데이터 원본 시각·상대 경과 시간과 프로그램 monotonic 관측·기록 시각을 구분한다. 속도를 높인 파일 분석의 처리 지연을 원래 공격 시작 대비 탐지 지연으로 혼용하지 않는다. 파일 경계·기록 중단·역순 시각을 실제 ECU suspension으로 자동 판정하지 않는다. |
| 정상 기준·평가 분리 | 정상 기준을 정하는 데이터와 최종 평가 데이터를 구분한다. 같은 capture/주행의 인접·중복 frame을 무작위로 나눠 평가 결과가 새 주행 성능인 것처럼 보이지 않게 한다. 분할 단위·파일 목록과 조정에 사용한 자료를 남기고 최종 평가 자료로 임계값을 맞추지 않는다. |
| 다른 데이터셋 평가 | 차량·버스·ID와 라벨 의미가 다르면 정렬·매핑 근거를 별도로 기록한다. 주 데이터셋의 ID·물리 범위를 다른 차량에 그대로 복사하지 않는다. 대상 차량의 정상 자료로 보정했다면 보정 사실과 평가와의 분리를 보고한다. |
| 가상 CAN 재생 시 | §7.3의 소유 marker와 송신 제한을 유지한다. 원본 rate가 제한을 초과하면 그대로 재생했다고 주장하지 않으며, 직접 파일 분석 또는 시각·속도 변환 중 선택과 영향을 먼저 확정한다. 원본 frame의 ID·payload를 SIL 형식에 억지로 맞추지 않는다. |

외부 데이터셋 평가는 해당 데이터셋이 실제 제공하는 정상·공격 구간으로 보고한다. 부족한 길이를 반복해 정상 30분의 독립 표본을 확보했다고 하거나 같은 파일을 5회 읽은 것을 서로 다른 공격 표본 5개로 표현하지 않는다. 기존 SIL의 정상 30분·공격별 5회·1초 합격 기준은 §7의 SIL 시험에만 적용한다. 외부 데이터에서 충족되지 않는 기존 가정은 §2.1.1에 따라 실제 자료를 우선해 갱신하며, 라벨·관측 정보로 산출할 수 있는 평가 단위·지연 정의와 실제 결과를 명시한다. 새 수치 합격선처럼 관측 사실만으로 결정할 수 없는 선택은 별도 확정한다.

제공기관의 다음 설명을 2026-11-24에 확인했다. 이 표는 원본 측정값과 구분한 출처 설명이며, 실제 파일 분석 결과는 별도 evidence에 연결한다. 후속 사용자 제공 ZIP으로 AutoHack 원본 분석과 독립 검산을 완료했다. ROAD 원본 분석은 아직 수행하지 않았다.

## 4. 현재 SIL의 CAN 보호 형식과 검사 순서

현재 주기 PDU는 Classical CAN, 11-bit ID, DLC 8이다.

| 항목 | 기준 |
| --- | --- |
| Counter | byte 6 상위 4-bit, `0~15` 순환 |
| Validity | byte 6 bit 3 = valid, bit 2 = degraded, bit 1 = fault |
| Reserved | byte 0~5에서 신호에 쓰지 않는 bit와 byte 6 bit 0은 0 |
| 프로젝트 CRC | byte 7, polynomial `0x1D`, init `0xFF`, final XOR `0xFF`, 반전 없음 |
| CRC 입력 | CAN ID의 2-byte big-endian 표현 + payload byte 0~6 |
| Counter 차이 | `delta = (현재 counter - 이전 counter) mod 16` |
| Counter 판정 | 최초 수신은 기준 설정, `1` 정상, `2~3` 수락하며 손실 기록, `0` 중복 거부, `4~15` 점프·역행 거부 후 재동기화 |

**여기서 CRC 변조는 payload byte 7의 애플리케이션 CRC 변조다.** CAN controller가 처리하는 물리 frame CRC 오류 주입이나 실제 bus-off 시험이 아니다. A3의 reserved 변조도 위 payload reserved bit를 뜻하며 CAN wire의 제어 필드를 직접 변조하는 시험이 아니다.

검사 순서는 기존 Gateway와 맞춘다.

1. frame 형식 확인 후 ID를 분류한다.
2. 주기 PDU의 ID → DLC → CRC → reserved를 검사한다.
3. 구조 검사를 통과하면 ID별 counter 상태를 검사한다.
4. valid flag → 신호 범위를 검사한다.

DLC가 틀리면 byte 6·7을 먼저 읽지 않는다. CRC/reserved 오류 frame은 counter 상태를 바꾸지 않는다. 기존 `CounterChecker`는 `4~15`를 거부해도 수신 counter로 재동기화하고, Gateway는 counter 검사 뒤 valid·범위를 확인한다. IDS가 독자적으로 다른 순서나 재동기화 정책을 적용하려면 기준서 변경과 영향 시험이 필요하다.

`15→0`은 정상이다. 4-bit counter만으로 큰 순방향 점프와 역행의 실제 원인을 구분할 수 없으므로 관측 delta를 기록하고 공격 의도를 단정하지 않는다. `2~3`을 A6 공격 이벤트로 처리해서도 안 된다.

기존 codec은 첫 실패 원인을 반환한다. CRC와 reserved가 함께 틀린 frame은 CRC 오류만 반환할 수 있다. A3 reserved fixture는 CRC를 다시 계산하고, A4 범위 fixture는 CRC·reserved·counter·valid 조건을 먼저 만족시켜 목표 검사에 도달하게 한다.

## 5. 공격별 탐지 제작 기준

아래 이벤트 표현은 구현자가 구분해야 할 의미다. 기존 codec 오류 이름은 그대로 표기하고, 횟수·누락 규칙의 최종 `rule_id`와 JSON schema는 §10에서 확정한다. **Replay라는 공격 label 자체를 IDS가 관측한 사실처럼 출력하지 않는다.**

이 표의 구체 byte·counter·신호값은 현재 SIL 프로파일 기준이다. 외부 데이터셋의 A1~A8 대응과 적용 가능한 규칙은 §3.3의 원본 확인을 거쳐 정하며, 대응 공격이 없거나 정의가 부족하면 평가 범위 밖으로 표시한다.

| 시나리오 | 필수 탐지 조건 | 기대 이벤트·근거 | fixture 및 주의사항 |
| --- | --- | --- | --- |
| A1 Flooding | 등록된 주기 PDU의 1초 window 관측 횟수가 ID별 예상 횟수의 3배를 **초과** | ID별 전송 횟수 초과. count, 정상 예상 횟수, 배수, window 기록 | 한도 안에서 목표 ID를 반복 전송. 다른 오류만 발생한 것으로 A1 합격 처리하지 않음. `vcan` 결과로 실제 arbitration DoS 성공을 주장하지 않음 |
| A2 Unauthorized ID | 실행 구성에 등록되지 않은 CAN ID 수신 | `ERR_UNKNOWN_ID`, 원본 ID·DLC·payload | `0x123`, `0x7FF`는 현 구성에서 확인 후 사용. 진단 ID를 미등록 ID로 오인하지 않음 |
| A3 Fuzzing | 정상 주기 PDU ID의 DLC 불일치 또는 payload reserved bit가 1 | `ERR_DLC` 또는 `ERR_RESERVED` | DLC와 reserved를 별도 시험. reserved 변경 후 프로젝트 CRC 재계산. 길이가 틀린 frame을 정상 decoder에 무조건 전달하지 않음 |
| A4 Out-of-range spoofing | 정상 ID·DLC·CRC·reserved·counter·valid를 만족한 신호가 정의된 min/max 밖 | `ERR_RANGE`, 신호명·raw 값·물리값·허용 범위 | RPM 9000 또는 speed 300 km/h. 정상 경계 8000 rpm·250 km/h와 함께 비교. 주입 frame의 counter 충돌로 범위 검사가 가려지지 않았는지 확인 |
| A5 CRC 변조 | 정상 ID·DLC의 byte 7이 재계산한 CRC와 다름 | `ERR_CRC`, 수신 CRC·계산 CRC | 다른 필드는 정상이고 byte 7만 변경. CRC 불량 frame이 counter 상태를 이동시키지 않는지 확인 |
| A6 Counter 변조 | 구조상 정상인 PDU의 delta가 `0` 또는 `4~15` | `ERR_COUNTER_DUPLICATE` 또는 `ERR_COUNTER_JUMP`, 이전·현재 counter와 delta | 중복·역행·점프를 각각 시험하고 CRC 재계산. 최초 frame은 비교 기준이 없으므로 사전 정상 입력 필요 |
| A7 Replay | 재생 frame에서 A6 counter 이상 또는 A1 횟수 초과 조건이 성립 | 해당 counter 이벤트 또는 ID별 전송 횟수 초과 이벤트 | 정상 trace 원본과 재생 간격을 보존. 단순히 같은 payload가 나타난 사실만으로 Replay 확정 금지. 미탐 가능한 조건은 §9에 기록 |
| A8 Suspension | 대상 주기 PDU의 메시지 누락이 정상 주기의 3배 이상 | 메시지 누락 이벤트, 대상 ID·마지막 관측 시각·경과 시간·주기 | 입력이 전혀 없어도 timer로 검사. 대상 ECU의 송신을 멈추는 통제된 시험이며 CAN frame 주입만으로 ECU 정지를 입증한 것이 아님 |

`project.md` §10의 공통 사건 필드는 다음과 같다. 최종 key 이름과 타입은 구현 전에 확정한다.

### 6.1 대시보드 연동 기준

대시보드는 IDS 결과를 실시간으로 확인하고 과거 실험을 조회하는 모니터링 화면으로 연결한다. 논리적인 데이터 흐름은 **CAN 관측 → IDS 판정 → 공통 이벤트 기록·저장 → 조회 API → 대시보드**다. 실제 프로세스 배치와 전달 방식은 §10에서 확정하며, 화면이 탐지 규칙을 별도로 구현하거나 CAN을 직접 읽도록 만들지 않는다.

| 화면에서 확인할 내용 | 연결할 근거 |
| --- | --- |
| 실시간 탐지 목록과 상세 | 발생 시각, rule ID, severity, CAN ID, 관측값·임계값, 원본 trace 연결 |
| ID별 트래픽과 누락 상태 | 관측 횟수, 실제 측정 구간, 주기, 마지막 관측 시각, freshness. 실제 bus utilization으로 표시하지 않음 |
| 실험별 결과·이력 | experiment ID, 적용 구성·정책 버전, 저장된 이벤트와 사후 시험 평가 |
| IDS·수집·저장·화면 연결 상태 | 마지막 갱신 시각, 연결 끊김, 수집 손실·기록 적체. 데이터 없음과 정상 무탐지를 구분 |
| 향후 IDPS 동작 이력 | 연결된 탐지 이벤트, 적용 정책과 실제 실행 결과. 아직 예방 기능이 없으면 미구현 상태를 표시 |

`project.md` §10에 따라 SQLite 저장과 FastAPI 조회를 연결하는 방향으로 설계한다. WebSocket/SSE 선택, endpoint·포트·접근 범위·인증 정책·갱신 주기·재연결 시 누락 복구 방식은 아직 확정하지 않는다.

탐지 결과와 화면 표시가 같은 이벤트를 가리키도록 이벤트 식별·schema 버전·정렬·중복 처리 계약을 정한다. 공격 label과 TP/FP·탐지 지연 등 사후 평가 결과는 실시간 IDS 관측과 구분해 표시한다. 화면에서 이벤트를 확인했다고 원본 탐지 기록이 바뀌거나 예방 조치가 실행되어서는 안 된다.

대시보드 정지·연결 끊김·느린 소비자 때문에 탐지 또는 ECU/Gateway 통신이 멈추지 않아야 한다. 재연결 후 조회와 실시간 표시의 누락·중복, 저장 건수와 표시 건수, 최신성 표시를 시험한다. 표시 지연은 기존 1초 탐지·기록 기준과 구분해 측정하며 새 화면 지연 합격값은 임의로 정하지 않는다.

### 6.2 향후 IDPS 확장 기준

확장 시에는 **탐지 사실 → 예방 정책 판단 → 허용된 대응 실행 → 결과·복구 기록**을 구분한다. 이는 후속 설계 요구이며 현재 별도 대응 프로세스나 제어 경로를 확정한 것은 아니다. IDS 판정은 대시보드나 예방 기능이 없어도 독립적으로 시험할 수 있어야 한다.

- 원래 탐지 이벤트를 보존하고 예방 정책 버전·판단 이유·대상·요청 동작·실제 성공/실패·해제 및 복구 이력을 연결할 수 있게 계약을 확장한다. 필드명·타입·식별자 형식은 구현 전에 확정한다.
- 모니터링 대시보드의 기존 차량 제어권 경계를 유지한다. 향후 화면에서 정책 변경·대응 승인을 수행하려면 권한과 제어 경로를 별도 결정한다.
- Gateway 전달 거부, 진단 요청 제한, 송신 주체 격리 등은 후보 동작이다. 선택 전에 관측 위치와 실제 적용 가능한 경계를 확인한다. 같은 CAN에서 이미 수신된 frame을 사후 탐지만으로 제거했다고 주장하지 않는다.
- 탐지만 수행하는 단계, 조치 후보만 기록하는 검증 단계, 실제 예방 동작을 적용하는 단계의 도입 여부와 전환 조건을 후속 설계에서 결정한다. 오탐에 의한 정상 통신 손실과 조치 실패 시 동작, 적용 한도·해제·복구 기준도 함께 정한다.
- IDPS 전후는 동일한 구성·시나리오·관측 지점에서 비교한다. 탐지 성공, 실제 예방 효과, 정상 트래픽 영향, 복구 여부를 각각 측정한다. 탐지 이벤트 발생만으로 차단 성공을 판정하지 않는다.

## 7. 시험 및 합격 기준

### 7.1 정상 기준선

- 정상 주행 시나리오를 30분 동안 1회 실행한다.
- 공격 탐지 이벤트 오탐은 0건이어야 한다. CRC/counter 오류, process crash와 무제한 queue 증가가 없어야 한다.
- 정상 ISO-TP 진단을 사용하는 구성에서는 그 트래픽도 정상으로 분류되는지 확인한다.
- `15→0`, counter delta `2~3`, 신호 min/max, 등록 ID와 DLC 8의 정상 fixture를 확인한다. delta `2~3`의 손실 기록을 공격 오탐과 구분한다.
- CPU·RAM peak와 기록 경로의 적체·누락을 확인한다. 숫자로 된 추가 자원 합격선은 임의로 만들지 않는다.

### 7.2 공격 시험

- A1~A8 각각 seed를 고정해 5회 실행한다. A3의 DLC/reserved와 A6의 중복/역행/점프는 세부 시험으로 구분하고 결과를 섞지 않는다.
- 각 실행에서 **§5의 해당 기대 이벤트가 발생하고 공격 시작 후 1초 안에 기록**돼야 한다. 다른 규칙의 이벤트만으로 대체 합격하지 않는다. A7은 명시한 counter 또는 횟수 규칙으로 평가한다.
- A1은 경계 count `3E`와 `3E+1`, A4는 범위 안/경계/밖, A8은 `3T` 직전/도달을 fixture로 확인한다. 시각 경계 시험은 §10의 정책 확정 뒤 정확한 입력 시각을 고정한다.
- A8은 전체 CAN 입력이 멈춰도 검사되며, ECU 하나가 여러 PDU를 송신하면 함께 중단된 ID와 발생 이벤트를 기록한다. supervisor의 자동 재시작 여부도 실행 조건에 남긴다.
- 공격 종료 뒤 정상 송신·수집·기록이 복구되는지 확인한다. counter 재동기화 뒤 연속 오탐 여부를 기록한다.
- 실행별 기대 이벤트 유무, 최초 탐지·기록 지연, 추가 이벤트, 수집 손실과 실패 사유를 보고한다. 반복 5회 중 일부만 성공한 결과를 전체 통과로 쓰지 않는다.
- 정답 label과 이벤트의 연결은 사후 평가기가 수행한다. 혼동행렬을 보고할 때는 frame/시간 구간/실행 중 평가 단위와 TP·FP·FN·TN 정의를 먼저 확정한다.

### 7.3 공격 도구의 실행 조건

`project.md` §11.3의 제한을 그대로 따른다.

- 프로젝트가 생성한 `vcan`/`vxcan`만 사용하고 물리 CAN은 거부한다.
- 최대 1000 frame/s, 최대 10초, 최대 10,000 frame을 모두 지킨다. Ctrl+C와 timeout으로 중단한다.
- `/run/vehicle-sil/owned-interfaces.json`의 현재 `run_id`, namespace, interface, kind를 실제 `ip -details -json link show` 결과와 대조한다. marker 누락·불일치는 실행 거부다.
- Replay 입력은 ID·DLC·길이·시간 간격을 검증한다. 원본 trace가 제한을 넘는다고 무제한 재생하지 않는다.
- frames/s와 payload bytes/s를 기록한다. 이를 실제 CAN bus utilization으로 환산하지 않는다.
- A8의 송신 중단은 CAN 송신 제한과 구별해 대상·중단·복구 절차를 기록한다. 다른 프로세스를 임의로 종료하도록 범위를 확장하지 않는다.

## 8. 구현 순서와 완료 산출물

1. §3.3의 데이터셋 조합·파일·입력 방식과 §10의 적용 항목을 결정하고 `project.md`와 정책 원본에 반영한다.
2. 공통 CAN/진단 정의를 읽고 입력 분류와 기존 codec 오류를 확인한다.
3. A2·A3·A4·A5의 단일 frame 검사, A6의 ID별 counter 상태를 구현한다.
4. A1의 시간 window와 A8의 독립 timer를 구현하고 A7을 기존 규칙에 연결한다.
5. 공통 사건 필드와 비동기 기록을 연결하고 trace 기반 재현·경계 fixture를 검증한다.
6. 정상 30분과 공격별 5회 시험 후 결과를 집계한다.
7. §6.1의 조회·실시간 대시보드를 연결하고 저장·표시 일치성과 중단·재연결을 검증한다.
8. IDPS로 확장할 때 §6.2의 예방 정책·적용 위치·권한·복구 기준을 먼저 확정하고 별도 구현·효과 시험을 수행한다.

공격 계획의 1차 우선 대상은 A1·A2·A4·A5·A6·A7이다. A3·A8도 이번 CAN 제작 기준에 포함한다. B2·B3가 원문 계획의 1차 목록에 있다는 사실은 유지하되, 이 CAN 문서만으로 전체 Phase 7 완료를 선언하지 않는다.

IDS 완료 시에는 소스·실행 안내, 확정된 정책, 정상/공격 fixture, 시나리오-규칙-시험 추적표, 로컬 결과와 공유용 evidence가 있어야 한다. 대시보드 연동 완료에는 API·이벤트 계약, 화면과 저장의 일치성 및 장애·재연결 시험 근거를 추가한다. IDPS 예방 기능의 완료는 별도 기준과 시험으로 판단한다. 현재 AutoHack·HCRL 원본 분석과 외부 AutoHack용 C11 네 규칙 구현·파일 평가를 완료했다. 전체 SIL·수집·대시보드·IDPS 완료를 뜻하지 않는다.

## 9. 탐지 한계와 보고 표현

- CRC와 counter는 인증이 아니다. 공격자가 이를 맞추고 허용 범위 내 값을 보내면 기존 규칙으로 진위를 확정할 수 없다.
- 4-bit counter는 순환한다. 오래된 frame이 현재 기대 counter와 맞고 횟수도 기준 이하라면 A7 Replay를 놓칠 수 있다. 모든 Replay 탐지를 보장하지 않는다.
- A1은 정의된 횟수 이상, A8은 메시지 누락을 탐지한다. 이 사실만으로 공격 의도·원인·실제 ECU 피해를 확정하지 않는다.
- `vcan`/`vxcan`은 arbitration, 전압, 물리 오류, bus-off를 재현하지 않는다. 낮은 숫자 ID의 실제 버스 우선권이나 물리 DoS를 입증한 것으로 쓰지 않는다.
- 합성 정상 trace의 오탐 0건과 1초 탐지 결과는 해당 VM·구성·시나리오에 한정한다. 실차 탐지율, 양산 IDS 적합성 또는 R155 형식승인을 의미하지 않는다.
