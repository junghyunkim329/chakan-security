## 0. 큰 그림 (5분)

```
[엔진 ECU]  ┐
[브레이크 ECU] ├─ CAN 메시지(8바이트) ─→ [Gateway] ─→ (Phase 3) ─→ [중앙 컴퓨터]
[조향 ECU]  ┘
```

- ECU = 부품 하나를 맡은 작은 컴퓨터. 자기 상태를 **정해진 주기**마다 CAN으로 방송
- 받는 쪽은 메시지를 믿기 전에 **검사**부터 함 (깨졌나? 빠졌나? 이상한 값인가?)
- Phase 2 = 보내는 쪽(ECU)과 검사 규칙(codec)을 만든 단계

## 1. CAN 기초 ⭐ 가장 중요

**① 개념**
- CAN은 IP 주소가 없음. 메시지마다 **ID**(예: `0x100`)를 붙여 **모두에게 방송**, 필요한 쪽이 골라 들음
- ID가 **작을수록 우선순위가 높음** (동시에 보내면 작은 ID가 이김 = arbitration)
- Classical CAN: ID 11비트(0x000~0x7FF), 데이터 최대 **8바이트**
- DLC = 데이터 길이(0~8)
- 실제 CAN에는 하드웨어 CRC도 있음 → 우리 byte 7 CRC와는 **별개** (우리 건 소프트웨어 E2E 보호)

**② 코드**: `config/signals/can.yaml`의 `id`, `dlc`

**③ 해보기**
```bash
ip netns exec hj_gw candump vxcan_gw                    # 터미널 A
ip netns exec hj_veh cansend vxcan_veh 123#DEADBEEF     # 터미널 B
```

**④ 질문**
1. `0x100`과 `0x200`이 동시에 보내면 누가 먼저?
2. 왜 엔진·브레이크(0x100, 0x180)가 진단 요청(0x7E0)보다 ID가 작을까?

## 2. 16진수와 바이트

**① 개념**
- 1바이트 = 8비트 = 0~255 = `0x00`~`0xFF`
- 16진수 한 자리 = 4비트. `0xA8` = `1010 1000`
- 비트 번호는 오른쪽부터 bit0

**② 코드**: 모든 곳. 특히 `candump` 출력 읽기

**③ 해보기**: 계산기(프로그래머 모드)로 `0x03 0x20` → 800 확인

**④ 질문**
3. `0x1F40`은 10진수로? (힌트: 엔진 최대 회전수)
4. `0xA8`에서 bit3은 0일까 1일까?

## 3. 신호를 바이트에 넣는 법 (인코딩) ⭐

**① 개념**
| 개념 | 뜻 | 예시 |
| --- | --- | --- |
| **scale** | 실제값 = 저장값 × scale | 시속 60km, scale 0.01 → 저장값 6000 |
| **big-endian** | 큰 자리 바이트를 앞에 | 6000 = `0x1770` → `17 70` |
| **signed (2의 보수)** | 음수 표현법 | -40.0℃ → -400 → `0xFE70` |
| **bitfield** | 1바이트를 비트 단위로 나눠 여러 on/off 저장 | byte5: bit0 시동, bit1 회전 중 |
| **reserved** | 안 쓰는 칸, 항상 0 | 0x180 byte 4~5 |

**② 코드**
- `src/common/pdu_codec.c` → `put_signal()`, `get_signal()`
- `tests/unit/test_codec.c` → `test_known_bytes()` (실제 바이트 예시)

**③ 해보기**: `ecu_engine` 실행하고 `candump`로 본 바이트를 손으로 해석
```
100 [8] 03 20 00 00 C8 03 08 xx
        └─rpm─┘ thr └coolant┘ flags
```

**④ 질문**
5. 냉각수 90.0℃는 어떤 2바이트로 저장될까?
6. 왜 scale을 쓰지 않고 그냥 실수(float)로 보내지 않을까?

## 4. CRC (검사 숫자) ⭐

**① 개념**
- 데이터로 계산한 **요약 숫자**. 보낼 때 붙이고, 받는 쪽이 다시 계산해서 비교
- 1비트만 바뀌어도 값이 달라짐 → **우연한 손상** 탐지
- 우리 프로파일: CRC-8/SAE-J1850 (다항식 `0x1D`, 초기 `0xFF`, 마지막 XOR `0xFF`)
- **CAN ID도 계산에 포함** → 다른 ID에 끼워 넣은 메시지도 탐지
- 표준 검사값: `"123456789"` → `0x4B` (구현이 맞는지 확인하는 방법)

**② 코드**: `src/common/crc8.c`, `tests/unit/test_crc8.c`

**④ 질문**
7. 해커가 rpm을 9000으로 바꾸고 CRC도 다시 계산하면 막을 수 있을까?
8. 왜 CRC 계산에 CAN ID를 넣었을까?

## 5. Alive counter (번호표) ⭐

**① 개념**
- 메시지마다 0→1→…→15→0 번호를 붙임 (4비트)
- 받는 쪽이 이전 번호와 비교: 같으면 **중복/재전송**, 건너뛰면 **누락**, 거꾸로면 **이상**
- 우리 규칙: 차이 1 정상 / 2~3 받되 누락 기록 / 0 거부 / 4 이상 거부 후 다시 맞춤

**② 코드**: `sil_counter_check()` in `pdu_codec.c`, `test_counter()` in `test_codec.c`

**④ 질문**
9. 마지막 번호가 15이고 다음이 0이면 정상일까?
10. 해커가 1초 전 메시지를 그대로 다시 보내면(replay) counter로 잡힐까? 항상?

## 6. 받는 쪽 검사 순서

**① 개념**: ID → 길이 → CRC → 예약 비트 → counter → valid → 범위
- **CRC를 counter보다 먼저** 보는 이유: 깨진 메시지의 번호표를 믿으면 번호 상태가 엉망이 됨
- **valid=0**: 보낸 쪽이 "이 값 믿지 마"라고 표시 (센서 고장 등)
- **범위 검사**: CRC가 맞아도 rpm 9000 같은 값은 거부

**② 코드**: `sil_pdu_unpack()`, `sil_pdu_check_values()`

**④ 질문**
11. CRC도 맞고 counter도 맞는데 거부될 수 있는 경우 2가지는?

## 7. 보안 관점: 무결성 vs 진위성 ⭐⭐ 발표 단골

| | 무결성 (integrity) | 진위성 (authenticity) |
| --- | --- | --- |
| 질문 | 내용이 **깨졌나?** | **진짜 그 ECU**가 보냈나? |
| 우리 프로젝트 | ✅ CRC·counter | ❌ 없음 |
| 실차 대응 | E2E 보호 | **SecOC** (비밀키 기반 MAC) |

- UN R155 Annex 5 **M10**: "수신 메시지의 **진위성과 무결성**을 검증해야 한다"
- 우리 CRC는 비밀키가 없어서 **해커도 다시 계산 가능** → 위조 못 막음
- 그래서 Phase 7 IDS로 "이상한 패턴"을 탐지 + 한계를 기록

**④ 질문**
12. SecOC는 CRC와 뭐가 다를까? (키워드: 비밀키, MAC, freshness)

## 8. 주기 송신과 시간

**① 개념**
- ECU는 **정해진 주기**(10ms, 20ms)마다 보냄. 받는 쪽은 "안 오면 이상"으로 판단 (§5.4 freshness)
- **monotonic clock**: 시스템 시간을 바꿔도 거꾸로 가지 않는 시계 → 주기 측정용
- **절대 시각 예약**: "지금부터 10ms 쉬기"가 아니라 "시작+10ms, +20ms…에 깨기" → 오차가 쌓이지 않음 (drift 방지)
- **jitter**: 매번 조금씩 흔들리는 정도. 우리 결과 약 1ms

**② 코드**: `src/common/ecu_runtime.c` → `sleep_until()`, `next[i] += period`

**④ 질문**
13. "10ms 쉬고 보내기"를 1000번 반복하면 왜 10초보다 길어질까?
14. 우리 결과가 실제 차량 ECU의 타이밍을 증명할까?

## 9. 프로젝트 구조와 도구

| 도구 | 하는 일 | 우리 파일 |
| --- | --- | --- |
| **YAML** | 사람이 읽기 쉬운 설정 형식 | `config/signals/can.yaml` |
| **코드 생성** | YAML → C 표 자동 생성 (손으로 두 번 안 씀) | `tools/codegen/gen_can_signals.py` |
| **CMake + Ninja** | 빌드 자동화 | `CMakeLists.txt` |
| **CTest** | C 시험 실행 | `ctest --test-dir build` |
| **pytest** | Python 시험 | `tests/unit/python/`, `tests/integration/` |
| **cppcheck** | C 코드 실수 찾기 | — |

**핵심 원칙: 단일 원본 (single source of truth)**
- 신호 정의는 YAML **한 곳**. C와 Python이 같은 파일 사용 → 서로 다르게 해석하는 버그 방지
- 그래서 C와 Python이 같은 바이트를 만드는지 **교차 확인** 시험이 있음

**③ 해보기**
```bash
cmake -S . -B build -G Ninja && cmake --build build && ctest --test-dir build
cat build/generated/sil_can_signals_gen.c    # YAML에서 생성된 C 코드 구경
```

## 10. 시험 설계 사고방식

| 시험 종류 | 질문 | 예시 |
| --- | --- | --- |
| 정상값 | 평범한 값이 잘 되나? | rpm 2500 |
| 경계값 | 끝 값은? 끝+1은? | 0, 8000 통과 / -1, 8001 거부 |
| 잘못된 데이터 | 이상한 입력을 거부하나? | 길이 7, CRC 틀림, 예약 비트 1 |
| 주기 | 시간 약속을 지키나? | 10ms ± 2ms |

- ISO/SAE 21434 테스트 매뉴얼의 **퍼징** 항목과 연결: "비정상 길이 CAN 프레임", "허용 범위 밖 데이터" → 우리 잘못된 데이터 시험이 이것의 기초
- **주장할 수 있는 것 / 없는 것** 구분하기 (vcan 결과로 실제 CAN 성능을 주장하면 안 됨)

## ✅ 답

1. `0x100` (ID가 작을수록 우선)
2. 실시간 제어 상태가 진단보다 중요해서 우선순위를 높게 (우리 ID는 프로젝트 선택값)
3. 8000
4. 1 (`1010 1000` → 오른쪽에서 4번째)
5. 900 = `0x0384` → `03 84`
6. CAN은 8바이트뿐이라 아껴야 함. 정수가 MCU에서 빠르고 정확함
7. ❌ 못 막음. CRC는 비밀이 없어서 누구나 계산 가능. 범위 검사(9000 > 8000)로는 잡힘
8. 0x180 메시지를 0x100인 척 끼워 넣어도 CRC가 달라져서 탐지
9. ✅ 정상 (15 → 0은 차이 1, 한 바퀴 돈 것)
10. 부분적. 바로 다시 보내면 중복으로 잡히지만, 번호가 한 바퀴(16개) 돈 뒤 맞춰 보내면 못 잡음 → counter는 인증이 아님
11. valid=0, 값 범위 초과 (그 전에 예약 비트 1도 있음)
12. SecOC는 **비밀키**로 만든 MAC을 붙임 → 키가 없는 해커는 못 만듦. freshness 값으로 replay도 막음
13. "쉬는 시간" 외에 계산·전송 시간이 매번 더해져서 오차가 쌓임 (drift)
14. ❌ 아님. 일반 리눅스 VM 프로세스 스케줄링 정확도일 뿐, MCU/RTOS 실시간성이나 실제 CAN 버스 타이밍은 증명 못 함
